# 評価履歴の参照API（SS）

Experimentの公開APIから、実行IDを起点に評価を探し、その測定結果、集計値、判断の根拠をたどる。実行全体のイベントや成果物は `history(run)` で参照する。[Experimentの公開インターフェース](01_experiment_api.md)・[Evaluatorの詳細設計](09_evaluator.md)

## 評価を探す

| 操作 | 取得できる内容 |
|---|---|
| `list_evaluations(run_id, *, limit, cursor=None)` | その実行で準備を始めた評価を開始順に返す。各項目に評価ID、状態、評価対象への参照を含む。読み出し中は対象範囲と各評価の状態を初回時点に固定する |
| `get_evaluation(run_id, evaluation_id)` | 評価対象、実際に適用した条件、現在の状態、終了した場合の理由、完了条件の判定、測定件数、元の評価への参照。準備中に失敗した場合は、そこまでに確定した情報と失敗理由を返す |
| `list_derived_evaluations(run_id, evaluation_id, *, relation=None, limit, cursor=None)` | 同じプロジェクトの実行をまたぎ、指定評価を直接の続行元・訂正元・再集計元とする評価を返す。`relation` で種類を絞れる。E1をE2、E2をE3で訂正した場合、E1からはE2を、E2からはE3を取得する |

個々の評価の準備を始める時点で評価IDを発行する。たとえば重みの読み込みで失敗しても、そのIDで評価を参照できる。学習の中断により後続評価を始めなかった場合は、実行履歴に `skipped` と理由を残し、評価IDは発行しない。

`get_evaluation` の `complete` はタスクが報告した判定を表す。未報告は `null`、判定済みで条件未達は `false`、達成は `true` とする。Experimentは件数や終了状態から判定を補わない。`result_count` はその評価IDで新たに確定した測定件数で、再送は一度だけ、実際の再測定は測定ごとに数える。発話単位の処理数や予定件数などの進捗はタスクが任意で添えられる。

元の評価への参照は、関係の種類（続行・訂正・再集計）、元の実行ID、元の評価IDの組で返す。訂正では理由を含め、複数の評価を再集計した場合は各入力評価を示す。

## 測定結果を読む

| 操作 | 応答 |
|---|---|
| `read_results(run_id, evaluation_id, *, limit, cursor=None, after=None)` | その評価が測定した結果を確定順に `results` として返す。`next_cursor` と、読み出し開始時点の `evaluation_state` を含む。同時に確定した複数件の順序も保存時に固定する |
| `get_result(run_id, evaluation_id, result_id)` | 一覧の1件と同じ形式で指定結果を返す。その評価に存在しなければ `not_found` |

1件の共通項目は、評価内で一意な `result_id`、何を測ったかを示す `target`、測定した値 `value` とする。後二者の内部形式はタスクが決める。同じ発話を2回測定した場合、同じ `target` でも結果IDは異なる。

E1の60件に続きE2で40件を新たに測定したとき、E2の一覧と `result_count` に含むのは40件である。100件分の集計に採用した結果は、集計IDから両方の評価をたどる。保存済みの測定だけを再集計した評価は、測定0件で集計値を持てる。

## 分割取得と差分取得

一覧の初回は、その時点で確定している範囲から最大 `limit` 件を返す。続きがある場合の `next_cursor` は中身を解釈せず次の要求の `cursor` に渡す。末尾では `next_cursor=None` を返す。進行中の評価でも同じ規則を使うため、評価状態は `evaluation_state` で確認する。

- **同じ読み出しを続ける場合**。カーソルは操作の種類、対象の実行・評価・集計などのID、絞り込み条件、初回の確定範囲と返却する状態、読み取り位置に対応する。同じカーソルと件数で再取得すると、同じ順序で同じ項目が返る。`limit` は途中で変更できる。
- **既知の位置から新しく読む場合**。`read_results` の `after` に同じ評価内の既知の `result_id` を指定すると、その測定の直後から、新しい範囲と評価状態で読み始める。ページ途中で処理を止めた場合にも、前回の末尾以降の増分だけを取得する場合にも使える。`cursor` と `after` を両方省略すれば先頭から読む。
- **セッションと移行**。カーソルは最初のプロセスやDB接続が終了しても使える。同じプロジェクト全体を正規の手順で移行して対象履歴を復元した場合も、移行元に接続せず、保存しておいたカーソルで元の範囲・状態・位置から続けられる。内部形式とDBでの実現方法は実装が選ぶ。[プロジェクト共通要件](../10_requirements/00_project_requirements.md#別の作業ディレクトリでの実験履歴の復元)

たとえば60件が確定した時点で20件を取得し、その後75件で評価が終了したとする。そのカーソルに `limit=5` を指定すれば、21～25件目と初回時点の評価状態が返る。その読み出しは60件目で終わる。60件目の結果IDを `after` に指定して新しく読めば、追加15件と終了後の評価状態が返る。

| 指定または状況 | 扱い |
|---|---|
| 既存の評価に確定結果が0件、または有効な `after` の後に結果が0件 | 成功。`results=[]`、`next_cursor=None` と読み出し開始時点の評価状態を返す |
| 指定した実行・評価、または評価内で指定した結果IDが見つからない | `not_found` と該当する対象を返す |
| カーソルの操作・対象・絞り込み条件が一致しない、または `cursor` と `after` を同時指定した | `invalid_request` と指定の不一致の理由を返す |
| `limit` が正の整数でない、またはプロジェクトが設けた上限を超える | `invalid_request`。上限超過では許容上限を示す。同じカーソルで件数を変えて再試行できる |

## 集計値と入力をたどる

| 操作 | 取得できる内容 |
|---|---|
| `list_aggregates(run_id, evaluation_id, *, limit, cursor=None)` | 初回時点で公開済みの集計を公開順に返す。各項目に評価内で一意な `aggregate_id`、集計条件、暫定値かどうかを含む。IDの形式はタスクが定める |
| `get_aggregate(run_id, evaluation_id, aggregate_id)` | 指定した集計値、適用した条件、暫定値かどうか |
| `read_aggregate_inputs(run_id, evaluation_id, aggregate_id, *, limit, cursor=None)` | 実際の計算に直接使った入力への参照。入力が多くても分割して取得できる |

測定を使った入力には種類と `(run_id, evaluation_id, result_id)`、公開済み集計を使った入力には種類と `(run_id, evaluation_id, aggregate_id)` を返す。たとえば各foldの正解率を等しく平均した場合、直接の入力は各foldの集計で、その参照先から個々の測定をたどれる。タスクは入力ごとの役割や重みを任意で添えられる。全入力で共通する条件は集計全体に記録できる。

同じ評価で全件の正解率と一部の発話の正解率を公開した場合、それぞれの集計IDから使用した入力を取得できる。評価進行中に保存する暫定集計と、後で確定する最終集計にも別々の集計IDを付ける。[集計の公開と再送](09_evaluator.md#集計の公開と再送)

## 判断と集計の逆引き

`record_decision` では根拠とした評価に加え、任意でその評価内の `aggregate_id` を指定できる。これにより、最終集計が公開された後も、実際に判断に使った暫定集計とその入力をたどれる。評価の失敗そのものを根拠とした場合は評価IDで記録する。

逆引きAPIは同じプロジェクト内で、指定した測定を直接使った集計、または指定した集計を直接使った集計・判断を返す。対象はExperimentに記録された参照とする。さらに先の利用先は、返された集計IDからたどれる。同じ測定が一つの集計で3回使われても、逆引きで返す利用先は1件である。3回分の使用とその役割・重みは `read_aggregate_inputs` で確認できる。
