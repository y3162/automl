# Trainerの詳細設計（SS）

## 学習の開始

ExperimentはTrainerの公開API `train` を呼び、「新規学習」か「再開」かを明示する。Trainerは確定済みの設定に従い、必要なDataset・Transform・Modelをそれぞれの公開APIで組み立てる。[実行フロー](../20_basic_design/01_execution_flow.md)

- **新規学習**では、Trainerの学習状態を新たに用意する。別枝で親のモデル状態を引き継ぎ、ヘッドを追加して学習する場合も新規学習に含む。
- **再開**では、Experimentが元の実行とその最後の有効な保存点を特定し、Trainerがプロジェクト・タスクの定義に従って再開可否を判定する。同じ枝で引き継いだ学習条件のもと、Model経由でその地点のモデル状態を完全復元し、対応する学習状態を復元する。手法が未対応の場合や、必要な状態の欠落・不適合がある場合は、理由を呼び出し側に伝える。[Modelの詳細設計](07_model.md) · [チェックポイントと学習再開](../20_basic_design/05_checkpoints_and_resume.md)

いずれの場合も、実際の開始状態の保存が完了してから最初の学習更新に進む。[保存点と実行開始状態](04_checkpoint_management.md)

## 分散学習

Experimentは一つの実行IDで学習を起動・追跡する。Trainerの個別実装は分散基盤を選び、ワーカーの起動・同期・停止を管理する。あるワーカーが停止した場合も、続行できるかを手法に従って判断し、学習の結果と理由をExperimentに渡す。

Trainerは各プロセスが学習に実際に用いた入力を同じ実行IDに対応付け、Datasetに伝える（`add`）。バッチを使う場合はその構成も伝え、バッチ全体と各プロセスの両方で使用内容を取得できるようにする。[Datasetの詳細設計](05_dataset.md)

## 保存点の受け渡し

Experimentは、対象の実行に紐づいた保存操作をTrainerに渡す。再開用の保存点を作るとき、Trainerは同じ地点のモデル状態・学習状態・進捗と、その状態に反映済みのデータ使用範囲を一緒に渡す。

```python
checkpoint_id = save_checkpoint(
    model_state=model_state,
    training_state=training_state,
    progress=progress,
    usage_range=usage_range,
    request_id=request_id,
)
```

`training_state` の内容・内部形式と `progress` の単位はTrainerの個別実装が決める。たとえば勾配蓄積の途中を再開可能と定めたタスクでは、その地点の勾配とデータ位置も揃える。ワーカーごとの乱数状態が必要なら、復元先のプロセスとの対応を含める。

複数の保存を並行して進める場合、Trainerは各保存点が学習のどの順に当たるかをExperimentが判別できる情報を保存依頼に含める。たとえば `progress` の更新番号で前後が分かれば、その番号を使える。何を使うかはプロジェクト・タスクが決める。同じ保存依頼を再送するときも、初回と同じ順序情報を渡す。

`usage_range` は保存を依頼する時点で固定する。その表現はタスクが決め、Datasetが対象の使用記録を特定できるものとする。たとえば単一プロセスでは最後に反映した使用記録のID、分散学習では各プロセスで反映済みの位置を使える。[Datasetの使用履歴](05_dataset.md#学習で使用したデータ)

再開用の保存点では、受け取ったモデル状態・学習状態・進捗を保存し、そこに反映された使用履歴の範囲をDatasetで対応付ける（`commit`）。Experimentは両方の完了を確認し、有効な保存点として履歴に登録して、その保存点の成果物IDを返す。`latest` は保持中の有効な保存点のうち学習順で最後のものを指す。状態の保存、使用履歴との対応付け、履歴への登録のいずれかに失敗した場合はTrainerに理由を伝える。保存点の保持方針はプロジェクト・タスクの管理側が決め、Experimentに削除する保存点IDを指定する。

Trainer が `context.prepare_model(components, name)` で選んだ部品名は開始状態と保存点に引き継ぐ。モデルを直接構築した場合も保存操作の `model_name` で指定できる。学習後の評価と保存点からの評価はこの名前でモデルを構築する。Trainer は学習後の評価に使う保存点の成果物IDを戻り値の `checkpoint` に含める。

複数のモデルを学習する場合は、`start_training` と `save_checkpoint` の `model_states` に、設定の部品名をキーとするモデル状態の辞書を渡す。Trainer の学習状態と合わせて一つの保存点として記録する。再開時は同じ部品名で `prepare_model` を呼び、モデルごとの状態を復元する。

保存点の選択に検証成績を使う場合、指標の向きや同点時の優先順は個別実装が定める。学習後の評価候補が0件の場合は、実験の意図を知る側が評価の扱いと理由をExperimentに渡す。[学習と評価の組み立て](../20_basic_design/01_execution_flow.md#学習と評価の組み立て)

### 保存依頼の再送

`save_checkpoint` の `request_id` は任意で、同じ実行内の保存依頼を識別する。同じID・同じ内容の依頼が複数届いた場合は、同時に届いた場合も含め、一つの保存依頼として扱う。モデル状態・学習状態の保存と指定した使用範囲の `commit` を一度だけ確定し、確定した保存点IDを返す。保存完了後に応答が途切れて再送された場合も、初回の保存点IDを返す。

同じ要求IDでモデル状態・学習状態・進捗・使用範囲のいずれかが異なる場合は、相違した項目を示して `invalid_request` を返し、元の依頼を保持する。要求IDを省略した場合は通常の保存依頼として扱う。

Datasetから使用記録の不足が報告された場合、Experimentは不足範囲をTrainerに返す。分散実行の場合は該当するプロセスも伝える。記録が揃った後、Trainerは同じ要求ID・同じ内容で保存依頼を再送できる。Experimentは元の保存点候補について `commit` の完了を確認してから公開する。[Datasetの使用履歴](05_dataset.md#学習で使用したデータ)

## 停止条件と中断要求

どの保存の完了を学習の成功条件に含めるかは、実験の意図に応じてプロジェクト・タスクごとに決める。たとえば更新1000の重みを残すことが目的なら、Trainerは更新1000の保存点が確定してから学習成功をExperimentに返す。途中再開のための定期保存であれば、最後の保存がまだ進行中でも、タスクの成功条件を満たした時点で学習成功を返せる。

保存に失敗した場合、Experimentはその保存が学習の成功条件に含まれるかにかかわらず、保存対象の学習時点と失敗理由を元の実行履歴に記録する。たとえば学習が更新1000で成功し、その時点の任意の定期保存が容量不足で失敗した場合、履歴には学習成功と更新1000での保存失敗の両方が残る。最後に確定した有効な保存点が更新900なら、`latest` は更新900を指す。

Trainerは、停止条件に達し、学習の成功条件を満たした時点で終了理由もExperimentに返す。たとえば、学習中の評価で指標が所定の回数改善しなかったために早期終了した場合も、必要な保存が完了していれば学習は成功となる。実行計画に学習後の評価があれば、Experimentはその評価へ進む。

Experimentは、対象の実行に中断要求が届いているかを確認する手段を `train` に渡す。Trainerは安全に終了できる地点で停止を報告する。途中再開に未対応の場合や新たな保存点を確定できない場合もユーザーの要求で停止できる。Experimentは学習の安全な停止を確認して、学習を `interrupted` とする。並行評価がすでに失敗していれば実行全体は `failed` となる。失敗した処理がない場合は、同じ実行で進行中の評価を含めて停止を確認してから実行全体を `interrupted` とする。中断した学習の履歴には、利用可能な最後の保存点ID、または再開に未対応・有効な保存点がないなどの理由を残す。[中断要求](03_execution_state_and_processes.md#中断要求)

## 予期しない停止

実行プロセスの異常終了を確認した場合、Experimentは実行を `failed`、理由を `execution_failed` として記録する。すでに受け取ったログ・評価結果・成果物は、最後の有効な保存点より後のものも含めて保持する。監視だけが途切れた間は、最後に確認した状態に `state_confirmed: false` を付けて返し、枝の占有を維持する。プロセスの終了が判明しても成功または中断に必要な記録が欠けていれば、実行を `failed` とする。[実行状態とプロセス管理](03_execution_state_and_processes.md)

再開はユーザーまたはエージェントの依頼で行い、同じ枝に新しい実行IDを追加する。保存点Bの書き出し中に停止し、直前の有効な保存点がAなら、対応するTrainerはAから続ける。Aより後にDatasetが受領した各プロセスの使用記録も、元の実行から参照できる。再開元として記録するのは元の実行IDとAの保存点IDである。有効な保存点が一つもなければ、再開できない理由を返す。

並行評価は評価したモデル状態と結果の到着時点を別々に記録する。たとえば更新300の保存点の結果が更新320で届いた場合、再開後も300の保存点からその評価を参照できる。再開したTrainerがいつ結果を学習に使うかはタスクの再開条件で決める。判断順の再現が必要な手法は、保存時点でどの評価結果まで使用したかを学習状態に含める。[再開・分岐後の学習履歴](../20_basic_design/02_history_and_artifacts.md#再開分岐後の学習履歴)
