# 保存点と実行開始状態（SS）

## 保存点の識別

一つの保存点をチェックポイントの成果物IDで識別する。Experimentは、そのIDにモデル状態と学習状態の用途・保存先を対応付ける。保存点を新たに書き込んだときに ID を割り当てる。XOR Trainer は直前の保存点とモデル・学習状態・進捗・成績が一致する場合、そのファイルのハッシュを照合して ID を再利用する。欠落や破損時は有効な保存点を新たに作成する。[チェックポイントと学習再開](../20_basic_design/05_checkpoints_and_resume.md)

状態を保存するファイル名には、その学習手法の進捗を表す値（例：`epoch` や `step`）を含める。ファイル形式、ファイル数、同じ進捗でのファイル名の衝突を避ける方法、正本を保存するデータルート内のディレクトリ構成は個別実装が決める。

## 保存点の選択と保持

`latest` は、対象の実行で現在保持している再開可能な保存点のうち、学習順で最後のものを指す。モデル状態・学習状態の保存とDatasetの使用履歴との対応付けがともに確定してから公開する。更新400を削除し、更新300が残っていれば `latest` は300を指す。候補が尽きた場合は再開できない理由を返す。再開予定の実行では直近の有効な保存点の保持を推奨する。削除操作はその保存点にも適用できる。 [有効な保存点](../20_basic_design/05_checkpoints_and_resume.md#有効な保存点)・[バックアップ時の保持](../90_operations_and_maintenance/01_data_and_backup.md#バックアップ)

並行保存では、ExperimentはTrainerが保存依頼で示した学習順で `latest` を決める。たとえば更新301が先に確定し、その後で更新300が確定した場合、どちらも保存点IDで参照でき、`latest` は301を指し続ける。[Trainerの保存依頼](08_trainer.md#保存点の受け渡し)

成績で選ぶ場合、管理側またはタスクの個別実装が選択時に指標、順位、同点の扱い、選ぶ件数を決め、保存点IDをExperimentに渡す。過去の成績は削除済みの保存点を含めて調べられる。新たな学習・評価用に上位k件を求める場合は、利用できる保存点に絞ってから選ぶ。Experimentは受付時に指定されたID、または `latest` の解決先IDを記録する。明示されたIDが削除済みなら、そのIDと理由を返す。

たとえば管理側は検証精度の上位3件を残し、他の保存点を削除できる。順位による整理では、評価待ちの保存点は結果が確定するまで削除を保留することを推奨する。その間、保持数は一時的に3件を超え得る。完了条件に達しなかった評価の暫定値は通常の順位付けから外し、重みを残すかは保持方針で決めるのが推奨である。容量に上限がある場合や暫定値を順位付けに使う場合を含め、プロジェクト・タスクが方針を選べる。

## 使用中の保存点と削除

削除単位は保存点IDであり、その保存点に属するモデル状態と学習状態をまとめて削除する。`history(run)` の `artifacts` には、各保存点の `checkpoint_state` を `retained`（保持中）、`deleting`（削除中）、`deleted`（削除済み）のいずれかで返す。削除後も同じIDから進捗、評価結果、使用履歴をたどれる。

Experimentは、保存点の利用を受け付けた時点でその保存点を「使用中」とする。別の実行の開始に使う場合は、その実行の開始状態のコピーを保存し終えるまで使用中とする。同じ実行で学習から評価に進む場合は、Trainerが選んだ保存点IDで評価を受け付けた時点から、評価側がモデル状態を確保して元の保存点を削除しても評価を続けられるようになるまで使用中とする。

コピーやモデル状態の確保が終わる前に利用側が失敗・中断した場合、Experimentはその利用者が元の保存点をもう読み出さないと確認した時点で、その利用者の分だけ「使用中」を解除する。監視が途切れて読み出しの終了を確認できない間は、その利用を「使用中」に保つ。

| 状況 | 削除と利用の扱い |
|---|---|
| 利用を先に受け付けた | 一件でも使用中なら `delete_checkpoint` は通常の戻り値に保存点IDと `in_use` を含め、その依頼を終える。履歴上は `retained` のままとする。全利用者について使用中が解除された後、管理側は評価の途中でも改めて削除を依頼できる |
| 削除を先に受け付けた | ファイルを消す前に `deleting` を記録し、直ちに評価・分岐・再開の入力候補から外す。そのIDを指定した新規利用にはIDと削除状態を返す。新しい評価の起動依頼には実行IDを発行せず、`invalid_request` の `details` に `checkpoint_id` と `checkpoint_state`（`deleting` または `deleted`）を返す |
| 一部のファイルを削除した時点で停止した | `deleting` を保持する。同じIDで再依頼すると残りを削除し、すべての削除が完了してから `deleted` を記録する。完了後の再依頼にも削除済みと返す |

移行先の `verify()` は、`deleting` の保存点IDを削除未完了として報告する。削除途中に一部のファイルが残っていても、ほかに不整合がなければ `issues` は空で、CLIの終了コードは `0` となる。`deleted` の記録と実体の削除が整合する場合も正常とする。`retained` の保存点や利用側が保持する独立したコピーに欠落・破損があれば、`issues` にその実行ID・成果物IDと理由を含め、CLIの終了コードは `1` となる。[成果物の整合性検証](01_experiment_api.md#成果物の整合性検証)

## 実行ごとに保持する開始状態

各学習実行は、最初の学習更新に先立って、実際のモデル状態と学習の開始に必要なTrainerの状態を、その実行に属する独立した成果物として保存する。新規学習では初期化後、構造変更を伴う分岐では変更と部分初期化を適用した後、同じ枝での再開ではモデル状態と学習状態を復元した後に保存する。

評価のみの実行でチェックポイントを指定した場合も、評価を始める前に実際に評価するモデル状態の独立したコピーを保持する。予測結果を入力する評価では、入力に使った予測結果の実体を保持する。

Experimentは開始状態に必要な成果物をすべて保存した時点で、対象の成果物と保存完了を実行履歴に記録する。この記録の後に学習・評価の開始を記録し、処理に入る。実行プロセスの起動やモデルの初期化は、この保存完了より前に行える。保存途中で実行が終了した場合、途中まで書き出したファイルは開始状態として扱わない。

開始状態はその実行の確認・復元に使い、履歴の移行時にも引き継ぐ。生成元の保存点を削除しても、利用側に保存した開始状態は保持・検証する。評価実行のコピーの用途は、その評価の開始状態の確認・復元に限る。同じ重みを別の評価や分岐の入力に再利用したい場合は、元の保存点を残してそのIDを指定する。
