# Evaluatorの詳細設計（SS）

## 評価の呼び出し

TrainerとExperimentは、同じ公開API `evaluate` を使う。学習中はTrainerが評価時点のモデルと評価条件を渡す。Experimentからの評価で保存済みモデルを指定した場合、EvaluatorはModelの公開APIでその状態を復元する。保存済みの予測結果を指定した場合は、その結果を使う。評価結果を早期終了などの判断に使うかは呼び出し側が決める。[実行フロー](../20_basic_design/01_execution_flow.md)

プロジェクト内で生成した予測は成果物IDで指定できる。評価履歴からそのIDと予測を生成した実行をたどれる。外部ファイルで予測を渡した場合は、評価に使うファイルの内容を成果物として保存し、由来を外部入力と記録する。

たとえば実行R1が保存点C200を作り、別の実行R2がその保存点を評価したとする。ソースの変更を指定せずにC200を直接再評価するときは、R1に記録したEvaluatorの版を使う。R2を分岐元にして同じC200を再評価するときは、R2が実際に使ったEvaluatorの版を使う。重みはいずれもC200から復元する。[configの継承と上書き](02_configuration.md#継承と上書き)

学習直後の評価でも、保存点を指定した評価依頼をExperimentが受け付けると、評価側がモデル状態を確保するまでその保存点は使用中となる。削除が先に受け付けられていた場合は、評価を受け付けず、`invalid_request` の `details` に保存点IDと `checkpoint_state`（`deleting` または `deleted`）を返す。[使用中の保存点と削除](04_checkpoint_management.md#使用中の保存点と削除)

複数モデルの保存点を使うときは、Experiment がモデルごとの状態を復元し、設定の部品名からモデルを引ける辞書を Evaluator に渡す。学習中に複数のモデルを一緒に評価する Trainer も、同じ形式で渡せる。単一モデルの場合はモデルを直接渡す。

学習中は逐次評価を標準とする。並行評価を行う個別実装では、更新が進んでも同じ評価の全対象に評価開始時のモデル状態を使う。各結果からその状態を一意に識別できるようにし、後日も重みを復元できるように保持する評価時点はプロジェクト・タスクで選ぶ。評価の対象となった実行・保存点（またはモデル状態を特定できる進捗）と、結果が届いた時点の両方を記録する。後日あらためて測定する場合は、復元できるモデル状態または保存済みの予測結果を指定して新しい実行を起動する。[実行フロー](../20_basic_design/01_execution_flow.md)

## 評価開始の再送

実行内で個々の評価を開始するとき、呼び出し側は任意の `request_id` を指定できる。Experimentは実行IDごとにこの要求IDを照合する。初回は準備を始める時点で評価IDを発行し、要求ID・依頼内容・評価IDの対応を一度に記録する。

続行・訂正・参照用に保存する再集計では、呼び出し側は新しい評価の登録時に、関係の種類を `relation`、入力元すべての `(run_id, evaluation_id)` を `source_evaluations` で渡す。訂正では `reason` に訂正理由も渡す。Experimentはこの情報を新しい評価IDと一緒に記録する。これらの項目も同じ要求IDでの再送時に照合する。

同じ実行内で同じ要求ID・同じ評価対象と条件の依頼を再送すると、初回の評価IDを返す。同時に届いた場合も準備・測定は一度だけ行う。評価がすでに終了していても同じIDを返し、結果や失敗理由はそのIDで参照できる。同じ要求IDで評価対象や条件を変えた場合は `invalid_request` と食い違った項目を返す。

たとえば更新300の評価の受付直後に応答が途切れた場合は、同じ要求IDで元の評価IDを取得できる。同じ保存点を意図してもう一度評価する場合は、新しい要求IDで別の評価を開始する。要求IDを省略した開始依頼は、その都度新規の評価として受け付ける。

## 評価結果と完了条件

評価単位、結果の項目・形式、指標、集計方法、各結果が確定する時点、評価全体の完了条件はプロジェクト・タスクごとに定める。発話単位なら発話ごとに、話者単位なら話者ごとに結果を渡す。後者では各スコアから、その計算に使った発話を特定できるようにする。

個々の対象の評価に失敗した場合、Evaluatorは設定に従って再試行、打ち切り、または残りの対象の評価を行う。完了条件の達成・未達のどちらでも、結果は同じ形式で呼び出し側に返す。結果には、実際に適用した評価条件と完了条件の達否を含め、集計した対象、失敗・除外した対象とその理由を特定できるようにする。条件未達で指標や集計値を返す場合は暫定値と明示する。[Evaluatorの機能要件](../10_requirements/evaluator/02_functional_requirements.md)

たとえば100件のうち98件を集計し、2件が失敗した場合、全件の集計が完了条件なら98件の指標は暫定値となる。95件以上が条件なら同じ98件で条件を満たす。いずれの場合も、その指標を計算した対象と、失敗した2件の理由を確認できる。

実行計画に含まれる評価では、Experimentは完了条件を満たした評価を `succeeded`、通常終了して条件未達の評価を `failed` と記録する。完了条件の達否と、返された暫定指標や失敗・除外の理由は履歴に残す。学習成功後の評価が失敗した場合は学習の成功を保持し、実行全体を `failed` とする。評価の開始後にユーザーの停止要求で安全に終了した場合は、確定済みの対象別結果を保持し、評価を `interrupted` とする。並行する学習の失敗がすでに確定していれば、実行全体は `failed` となる。[実行状態とプロセス管理](03_execution_state_and_processes.md)

Trainerが学習中に呼んだ評価は、個々の評価の履歴に完了条件の達否を記録する。条件未達を受けて学習を続けるか打ち切るかはTrainerが判断する。

## 評価中の記録

学習中の評価でも単独評価でも、EvaluatorはExperimentが用意した共通の受け口を使う。対象ごとの結果が確定した時点で評価IDと、その評価内で個々の測定を識別する結果IDを添えて渡す。結果IDの形式は個別実装が選ぶ。各結果から対象ID、実際に使ったデータ、評価したモデル状態または入力予測を辿れるようにする。評価が途中で止まっても、確定済みの各結果と評価全体の完了状態を元の評価IDから確認できる。次の評価が未処理の対象から続行できるかは個別実装が定める。

同じ評価ID・結果ID・内容の再送には初回の記録を返す。同じ結果IDで内容が異なる場合は、食い違った結果を示して拒否し、確定値を保持する。同じ対象でも測定し直したときは新しい結果IDを付ける。評価終了を確定した時点で、その評価IDに含まれる確定結果の範囲も固定する。終了後も同一内容の再送に応答できる。中断後に遅れて届いた未登録の測定を採用する場合は、続行または訂正の新しい評価IDで記録する。

進行中の評価を分割して読み出す場合は、読み出し開始時点までの確定結果を重複・欠落なく取得できる。60件で読み始めた後に75件まで増えても、同じ読み出しの対象は60件で、追加の15件は次の読み出しで取得できる。一度に読む件数とDBで範囲を固定する方法は規模に応じて選ぶ。

評価IDは個々の評価の準備開始時に発行する。Experimentはこの評価で確定した測定だけを確定順に公開する。評価状態と完了条件の判定を別々に返し、判定が報告される前は `complete` を `null` とする。[評価履歴の参照API](10_evaluation_history_api.md)

進捗・診断ログは、評価中にも終了時にも評価IDを添えて同じ受け口に渡せる。ログの有無、内容、頻度は個別実装が決める。Experimentは受領したログを評価IDに対応付けて保持する。途中で最終結果が届かなくても受領済みログを参照でき、ログを出さない設定でも確定済みの対象別結果を参照できる。[履歴と成果物](../20_basic_design/02_history_and_artifacts.md)

Evaluatorの個別実装はプロジェクト・タスクで定めた完了条件に従って `complete` を判定する。失敗した評価を学習にどう使うかはTrainer、実験計画の成功・失敗の判定はExperimentが担当する。

## 評価の続行・訂正・再集計

中断した評価を続けるときは新しい評価IDを発行し、続行元の実行ID・評価IDを記録する。たとえば100件のうち元の60件と続行側の40件を集計した場合、集計から使用した各結果とその評価をたどれる。続行側で同じ対象を再測定した場合も両方を履歴に残す。どちらを採用したか、反復測定として両方を使ったかを集計から特定できる。異なる重み・データ版・指標実装の結果を合わせられるかは個別実装が判断し、Experimentは実際の評価条件と由来を記録する。

訂正は、その処理を行った実行に新しい評価IDを発行して記録する。たとえばラベル誤りの1件を再評価し、残り99件を再利用できる場合は、訂正元の評価と理由、再利用した99件、新たに採用した1件を訂正版からたどれる。元の評価と集計値を保持し、元の評価からも訂正版を参照できる。すでに行った判断や分岐は当時の評価IDに対応したまま残る。

データセットの版をまたぐ比較では、それぞれの版とサンプルIDを記録する。共通の発話IDなどで同じ対象とみなせるかは個別実装が定め、対応を示せないものは「対応不明」とする。旧版100件・新版90件の全件と、対応が確認できた80件での比較では集計対象が異なる。保存する比較結果から、採用した対象、入力評価・測定結果、集計条件をたどれるようにし、各版の元の集計も保持する。

保存済みの評価結果だけで試算する間は、新しい評価IDを発行しない。再集計値を後続から参照する評価結果として保存する時点で、再集計した実行に新しい評価IDを発行する。後日訂正・再集計する場合は新しい評価用の実行を起動する。たとえばR1とR2の結果をR3で再集計した場合、R3の評価の登録時に、再集計元としてR1・R2それぞれの評価を記録する。実際に採用した測定は、その集計を公開するときに入力として記録する。

## 集計の公開と再送

一つの評価で複数の集計を保存する場合、タスクは各集計に評価内で一意な `aggregate_id` を付ける。値、条件、暫定値かどうか、直接使った全入力の参照とその補足情報が揃った時点で一度に公開する。保存途中の集計は一覧にも個別取得にも出さない。たとえば5個のfoldの平均を保存中に4個目の参照で停止すれば、その集計は公開前である。一方、4個で計算した暫定平均は、その4個が揃えば公開できる。

公開後は同じIDで値・条件・入力を固定する。進行中の評価で60件の暫定集計を保存し、100件で最終集計を公開する場合は、同じ評価内で別の集計IDを付ける。途中集計の有無と頻度はタスクが決める。同じ評価ID・集計IDで公開内容がすべて一致する再送には、公開済みの1件を返す。数値が同じでも使用した入力、役割、重みなどが異なれば、食い違う集計を示して拒否し、元の記録を保持する。

## 測定結果の保存と評価終了の順序

Evaluatorはタスクの完了条件に従い、終了判定に必要な測定結果を決める。Experimentはそれらの保存が確定してから、または最後の結果と同じ操作で、評価終了を確定する。たとえば全100件が必要なら、評価の成功が参照できる時点で100件目まで取得できる。Evaluatorが最後の保存応答を確認してから終了を報告する方式でもよい。

タスクの成功条件に最終集計が含まれる場合、Experimentはその集計を評価の成功と同時か、それより前に公開する。たとえば「100件の正解率を出す」評価では、`succeeded` を確認した時点で正解率と採用した100件をたどれる。予測の保存だけが目的なら、必要な測定結果が揃った時点で成功にできる。後日新たに保存する再集計には別の評価IDを付ける。

成功報告が根拠として指定した集計の公開より先に届いた場合、Experimentは未公開の集計IDを示して応答し、評価を実行中のままにする。Evaluatorは集計の公開を確認してから同じ成功報告を再送する。Experimentはその再送を受けて成功を確定する。

通常終了で完了条件が未達となり、Evaluatorが暫定集計を返す場合は、Experimentはその集計と根拠となる測定結果を、評価の `failed` 確定までに公開する。`failed` を確認した時点で、失敗理由、暫定値、採用した測定結果を同じ評価から参照できる。

途中で中断した場合は、中断が確定した時点までに保存済みの結果を、その評価IDに属する範囲として保持する。

Evaluatorの終了報告が届く前にプロセスが異常終了した場合、Experimentはその評価が続行できなくなったことを確認した時点で、該当する評価IDを `failed` として終了する。異常終了の理由と、それまでに確定した測定結果を保持する。タスクが完了条件の判定を報告していなければ `complete` は `null` とする。監視が一時的に途切れている間は最後に確認した状態を保持し、終了の確定は続行可否を確認できるまで待つ。[実行状態とプロセス管理](03_execution_state_and_processes.md#監視が途切れた場合)

同じ評価IDで終了報告を再送した場合、終了状態・理由・`complete`・成功の根拠として報告された集計IDなどの内容が一致すれば、初回に確定した終了記録を返す。確定済みの内容と異なる場合は、食い違った項目を示して `invalid_request` を返し、最初の終了記録を保持する。

## 評価例

XOR の Accuracy と ErrorRate は、予定件数、集計件数、正解数、失敗・除外件数、必要件数、集計した ID を結果に含める。対象が空なら指標は `null`、`complete` は `false` になる。正解率が同じ二つの実験でも、比較時は `sample_ids` の集合を照合する。予測 JSON の構文不正と重複 ID は評価エラーとする。対象外 ID は件数を示す。ファイルにない予測は一度で失敗を確定し、`failed` に ID・理由・実際の試行回数を記録する。

固定版 XOR の test は 96 件ある。ID `104` の予測だけが欠けているとき、残る 95 件がすべて正解でも、完了条件によって実験の結果が変わる。

| 予測の状態 | 必要件数 | 正解数 / 集計件数 | 評価の結果 |
|---|---:|---:|---|
| 1 件欠落 | 96 | 95 / 95 | 正解率 1.0 は暫定値、評価は失敗 |
| 1 件欠落 | 95 | 95 / 95 | 正解率 1.0、評価は成功 |
| 欠落を修正 | 96 | 96 / 96 | 正解率 1.0、評価は成功 |
