# Datasetの詳細設計（SS）

## データセット版の作成と読み出し

Datasetの公開APIには、選択条件からデータセット版を作成する操作と、版を指定して開く操作を設ける。固定データでは、版を作成する時点でサンプルの構成と分割、各入力データの版、対応するラベルや正解データがある場合はその版と対応関係を固定する。学習中に抽選や生成を行う場合は、入力素材と生成方針の版を特定し、実際に選んだサンプルや生成条件を実行時の履歴に残す。

版を開くと、その版で固定した構成と内容を取得できる。たとえば、版 A の作成後にラベルを訂正しても、A からは訂正前のラベルを読み出せる。訂正後のラベルを使う版 B は、変更のなかった入力データの実体を A と共有できる。[Datasetの機能要件](../10_requirements/dataset/02_functional_requirements.md)

版の作成要求には識別子を付ける。同じ要求を再送した場合、Datasetが作成する版は一つである。すでに作成を完了していれば、初回の応答が届かず、その後に元データが追加された場合でも、作成済みの版を返す。現在のデータに同じ選択条件を改めて適用する場合は、新しい識別子で作成を依頼する。

同じデータ版と固定した分割名からは、別クローンへの移行や索引の再構築後にも同じサンプル ID 集合を返す。これは Dataset 実装者の責務で、保証する方法は各実装が決める。XOR CSV では固定版から求めた ID・分割・行位置と対応表を照合し、食い違う行があればその版の表を再構築する。

分割間の重複を検査するか、何を重複とみなすか、検出した場合に版を確定するかは、Datasetの個別実装が決める。検査条件の指定方法や結果の返し方も個別実装に委ねる。

## サンプルの識別と読み出し

サンプルは、データセット版と、その版の中で一意なサンプルIDの組み合わせで特定する。IDの形式や採番方法は個別実装が決める。異なる版の対象を比較するときは、共通の発話IDなど、タスクが定めた対応を使う。対応が分からない場合も各版の結果を個別に参照できる。[評価の続行・訂正・再集計](09_evaluator.md#評価の続行訂正再集計)

`open_version(version_id)` は、指定した版に固定された読み出し用オブジェクトを返す。別の版が作成された後も、このオブジェクトは開いた版を読み続ける。

Trainer・Evaluator は `context.open_dataset(components, name)` で版IDと読み出し用オブジェクトを取得できる。学習を同じ枝で再開するときは学習時の版を直接開く。評価でも、版を引き継ぐ場合はその版を開く。新たに版を作るときは `create_version` と `open_version` を順に呼ぶ。枝で初めて作る版の要求IDは枝IDと部品名から決まる。同じ枝でも、再評価で新版の作成を明示したときは、その作成依頼専用の要求IDを使い、同じ依頼の再送ではそのIDを再利用する。XOR 例では呼び出し側が使った版IDと分割名を実行履歴に渡す。

- `dataset.get_sample(sample_id)` は、その版から指定したサンプルを一件返す。
- `dataset.iter_samples(split="train")` は、その版の指定した分割からサンプルを順に返す。全件をメモリに載せずに処理できる。

ここで `dataset` は `open_version` の戻り値を表す。どちらの操作でも、各サンプルのID、データ本体、内容の解釈に必要なメタデータを取得できる。

## DBによるメタデータ管理

検索・参照を高速化するため、DatasetはサンプルのID・版、入力の対応関係、レシピ、使用履歴をDBで管理する。条件に合うサンプルの絞り込みやIDによる検索はDB上で行い、rawデータ本体は対象のサンプルを読み出すときに取得する。個別実装はプロジェクト・タスク所定のデータ量、並列数、検索条件に応じて索引を設計する。

参照するDBの数と入力の結び付け方はプロジェクト・タスクごとに決める。たとえば音声とラベルを別のDBから結び付ける場合、Datasetは返したサンプルから、使用時の音声とラベルそれぞれのID・版を特定できる情報を保持する。

### コーパスの索引

DuckDB を使う個別実装では、raw データと DB の対応を表す索引をコーパスごとに1テーブル設ける。コーパスには配置先に依存しない識別子を付け、テーブル名を `corpora.<corpus_id>`、raw データの入口を `data/corpora/<corpus_id>` とする。たとえば VCTK 0.80 と 0.92 は `vctk_0_80` と `vctk_0_92` で個別に参照できる。

1行が表す単位、キー、列名、型はコーパスごとに決める。テーブルに格納するのは、コーパス内の相対パス、配布元の識別子や注釈、原資料から取得できる属性など、そのコーパスに由来する情報に限る。配布元が定めた区分はコーパスの属性として扱い、実験のために決めた分割や複数素材の組み合わせは Dataset 版で管理する。

## 学習で使用したデータ

実行履歴には、学習に使ったデータセットの版と分割を記録する。`add` はTrainerなどの呼び出し側がサンプルを学習処理の入力として実際に用いたことを記録する。損失計算に用いたサンプルはパラメータ更新前に中断しても使用済みとなる。生成・ロード・先読みだけのサンプルは使用履歴の対象外とし、それらの記録を残すか削除するかは個別実装が決める。

個別実装は、その手法で意味を持つ使用順序と反復をDBから復元できる方式を選ぶ。固定分割を定めた順で使う場合は、版・分割・走査規則と実際に使った範囲で表せる。実行中に抽選・生成した場合は、たとえばサンプルIDと実際の抽選結果を順に記録する。

同じ使用記録の識別子で `add` が再送された場合、内容が一致すれば一度と数える。サンプルIDや使用順序などが食い違う場合は、最初に受理した記録を保持し、`invalid_request` と食い違った項目を呼び出し側に返す。同じサンプルを実際に二度使った場合は、それぞれの使用を区別して二度と数える。使用を識別する方法とDBでの記録単位は個別実装が定める。

バッチの有無と、一つのバッチに属する使用分は呼び出し側が定める。分散実行では、呼び出し側が示したバッチの構成と各使用分を対応付け、DBからバッチ全体でもプロセス別でも使用内容を取得できるようにする。一部のプロセスの記録だけが届いて中断した場合、受領済みの内容を返し、バッチ全体の記録は未完了、未受領のプロセスの使用状況は未確認と示す。バッチを定義しない手法では、実行に直接使用記録を対応付ける。

`commit` は、保存点の候補と、Trainerが保存依頼時に指定した使用範囲を対応付ける。たとえば更新300の状態を保存中に更新301の `add` が届いても、更新300の保存点に対応付けるのは300までの指定範囲である。301の使用分も元の実行履歴に残る。Experimentは状態の保存と指定範囲の対応付けの完了を確認してから、その保存点を再開可能として公開する。どちらかが未完了でも、直前の有効な保存点があればそこから再開できる。[チェックポイントと学習再開](../20_basic_design/05_checkpoints_and_resume.md)

指定範囲の使用記録が不足している場合、Datasetは未受領の範囲を返して、その `commit` 呼び出しを終える。分散実行では不足しているプロセスも示す。たとえば更新300に必要な4プロセスのうちプロセス3の記録だけが未着なら、プロセス3と不足範囲を返す。保存点は未確定で、`latest` は直前の有効な保存点を指す。残りの記録が届いた後、呼び出し側は元の保存依頼を同じ `request_id` と `usage_range` で再送できる。Datasetは指定範囲を改めて照合し、揃っていれば対応付けを確定する。

## 生成サンプルの登録と結果確認

呼び出し側は、一件の登録依頼に要求IDを付ける。`register_generated` は要求IDと登録内容（レシピ、生成物の実体、またはその両方）を受け取り、登録が完了するとサンプルIDを返す。登録が完了したサンプルだけを読み出し対象とする。

`registration_status` は要求IDで登録状況を返す。処理中ならその旨を、成功していれば登録済みのサンプルIDを、失敗していれば理由を返す。失敗後の再試行や応答が届かなかった場合の再送には、同じ要求IDを使う。

`get_generated(sample_id)` は登録済みのレシピと実体を `recipe` と `content` に入れて返す。取得時に未登録の項目は `None` とする。実体だけを登録した生成サンプルを学習に使う場合、Datasetは最初の使用前に、使用時の入力とその版、生成手順と版、実際に適用した条件を特定できるレシピを同じサンプルIDに対応付けてDBに保存する。以後はそのIDでDBからレシピを取得できる。必要なレシピを対応付けられない場合は学習への使用を拒否し、理由を呼び出し側に返す。

たとえば要求 `R1` で登録したサンプルが `S42` なら、応答が途切れても `registration_status` に `R1` を渡せば `S42` を確認できる。同じ要求が複数回届いても登録は一件とし、完了後の再送には同じ `S42` を返す。[Datasetの非機能要件](../10_requirements/dataset/04_non_functional_requirements.md)

## レシピの再生成と照合

実験を実装するエージェントは、プロジェクト・タスクで事前に定めた一致基準を個別実装に適用する。レシピの登録時には、適用した基準と判定に必要な情報を保持する。たとえばラベルは完全一致、特徴ベクトルは形状が同じで各要素の絶対差が指定値以下であることを条件にできる。後者では、許容差と比較の基準になる値を登録時に残す。

レシピには、入力データ、生成コード、使用したモデルの重みなど、再生成に必要な依存先の版を特定できる参照を記録する。同じ版の実体は複数のレシピで共有できる。依存先の各版の保持と生成物の実体の保存はプロジェクト・タスクの方針に従う。生成物の実体を保存しない場合も、レシピと依存先から再生成して所定の基準で照合できるようにする。[Datasetのデータ要件](../10_requirements/dataset/03_data_requirements.md)

呼び出し側はレシピに対応する処理を実行し、`verify_generated(sample_id, regenerated)` に再生成結果を渡す。Dataset は登録時の照合条件に従って一致・不一致を返す。照合の基準を取得できないときは、理由を伝えて失敗する。XOR の個別実装では、保存した実体またはレシピに含めた `expected_sha256` を基準に、JSON 化した内容の一致を確認する。

## データ配置とコーパスの入口

移動時に引き継ぐ正本は `data/store/` にまとめる。実行履歴、確定済み設定、保持する保存点、登録済みレシピがこれに当たる。コピーを省けるキャッシュ、一時生成物、再構築できる索引は `data/work/` に置く。DBも用途に従い、正本を含むDBは `data/store/` に、正本から再構築できる検索用DBは `data/work/` に置く。XOR CSV は `replay_files(settings, root)` で版の SHA-256 と実体を提示し、Experiment がストアの `inputs/` に一度だけ保存する。インラインの XOR データは確定設定に含まれる。

外部に配置するコーパスはユーザーが各計算機に必要な版を用意する。実験設定には、プロジェクトルートからの相対パスでコーパスの入口を記録する。各計算機では、その入口のシンボリックリンクを実体のディレクトリに向ける。たとえば実体名が一方で `LibriSpeech`、他方で `librispeech` でも、内部の構成が同じなら、Datasetは同じ入口とコーパス内の相対パスで同じサンプルを取得できる。[configの詳細設計](02_configuration.md)
