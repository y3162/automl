# 実行状態とプロセス管理（SS）

Experimentが受け付けた実行について、枝の占有、プロセスの起動、終了状態の確定を定める。[実行基盤と履歴の参照](../20_basic_design/06_execution_and_replay.md) · [Experimentの公開インターフェース](01_experiment_api.md)

## 受付と枝の占有

1. 要求IDがあれば先に受付記録を照合する。同じ内容の再送には初回のIDを返し、同じ要求IDで内容が異なる場合は理由を返す。新規要求についてはconfigと参照先を検証する。
2. 新規実行では、枝の占有確認と実行IDの `accepted` としての登録を一つの操作として行う。要求IDがある場合は、依頼内容と発行したIDの対応も同時に確定する。分岐と起動を一度に依頼した場合は両方のIDを対応付ける。同じ要求の同時再送でも作成・起動は一度とし、同じ枝を対象とする別要求との競合には `branch_busy` と進行中の実行IDを返す。
3. 受付後は確定済みconfigと実行に必要な情報を用意し、同じ計算機上に実行プロセスを起動する。呼び出し元のセッションが閉じた後も、実行と監視を継続する。

要求IDを指定して枝だけを作成する場合も、枝の作成と受付記録の保存を一つの操作として行う。同じ依頼を再送すると、初回の枝IDを返す。

枝の占有は `accepted` で始まり、`running` の間も続く。終了状態の確定と枝の解放は一つの操作で行う。別の枝は並行して実行できる。

## 状態の遷移

| 現在の状態 | 確認できた事実 | 次の状態 |
|---|---|---|
| `accepted` | 実行プロセスが起動した | `running` |
| `accepted` | 起動に失敗し、実行プロセスが動いていないことを確認した | `failed`。理由は `launch_failed` |
| `running` | 実行計画の全処理が成功し、プロセスが正常終了した | `succeeded` |
| `running` | 学習成功後に候補が0件となり、意図を知る側が理由とともに評価の見送りを報告した。他の処理は成功し、プロセスは正常終了した | `succeeded`。学習は `succeeded`、評価は `skipped` |
| `running` | 学習成功後に候補が0件となり、意図を知る側が必要な評価を実施できなかったと報告した | `failed`。学習は `succeeded`、評価は `failed` とし、報告された理由を記録する |
| `running` | 学習は成功し、同じ実行計画の並行評価がまだ進行中 | `running`。学習の状態は `succeeded` |
| `running` | 並行実行中に学習または評価が失敗し、他方は単独で続行中 | `running`。失敗した処理は `failed`、続行中の処理は `running` |
| `running` | 並行実行で一方が失敗した後、他方が成功し、実行が終了した | `failed`。各処理の結果・成果物と失敗理由を保持する |
| `running` | 並行する一方の失敗が確定した後、他方が停止要求に応じて安全に終了した | `failed`。失敗した処理を `failed`、停止した処理を `interrupted` とし、それぞれの終了理由を記録する |
| `running` | 逐次実行で学習が失敗し、後続評価が未開始 | `failed`。この時点で確定し、後続評価を理由付きで `skipped` とする |
| `running` | 実行計画の評価が中断要求による停止以外の理由で完了条件を満たさず、プロセスの終了を確認した | `failed`。理由は `execution_failed` |
| `running` | 失敗した処理がなく、中断要求に応じて進行中の処理が安全に停止したことをすべて確認した | `interrupted`。完了済みの処理はその結果を保持する。逐次計画で学習を停止した場合は、未開始の後続評価を `skipped` とする |
| `running` | プロセスが異常終了した、または終了した時点で、成功または中断に必要な処理結果が欠けている | `failed`。理由は `execution_failed` |
| `accepted`、`running` | 実行プロセスが終了したことは確認できたが、監視の停止などにより終了結果を確定できない | `failed`。理由は `execution_failed` とし、終了結果を確認できなかったことを記録する |

終了状態は実行IDごとに一度だけ確定する。学習と評価の状態は個別に記録する。学習後に行う評価は開始を待つ間は `pending` とし、前段の学習の失敗または中断が確定した時点で `skipped` に移し、その理由を記録する。開始した処理は `running` を経て `succeeded`、`failed`、`interrupted` のいずれかになる。処理の成功が記録された直後でも、プロセスが異常終了した場合は、取得済みの結果・ログ・成果物を保持し、全体の状態を `failed` とする。

## 監視が途切れた場合

監視側はプロセスの開始と終了結果を実行IDに対応付ける。再確認時に同じプロセスを識別できるよう、PIDと起動時刻などを記録する。

終了を確認できない間は、最後に確認した状態を `status` で返し、`state_confirmed: false` とする。この間、枝は占有したままにする。Experimentが終了を確認したら、取得できた処理結果とプロセスの終了情報を使って状態を確定する。取得済みのログ・成果物は履歴に残す。

## 中断要求

Experimentは対象の実行IDに要求を記録して受付結果を返し、その実行で進行中の処理に伝える。TrainerとEvaluatorは安全に終了できる地点で停止する。停止確認中も確定済みの対象別結果、指標、使用履歴、ログ、成果物は参照できる。

| 要求時に進行中の処理 | 停止を確認した後の記録 |
|---|---|
| 同じ実行の学習と並行評価 | 停止した学習・評価と実行全体を `interrupted` とする |
| 並行する一方がすでに失敗し、他方だけが進行中 | 実行全体は `failed`。先に失敗した処理の失敗理由と、他方が停止要求で `interrupted` となったことを履歴に残す |
| 逐次計画の学習が進行中で、後続評価は開始待ち | 学習と実行全体は `interrupted`。後続評価は `skipped` とし、理由に「前段の学習が中断されたため」と記録する |
| 学習が成功し、評価だけが進行中 | 学習は `succeeded` のまま、評価と実行全体を `interrupted` とする |
| 後日開始した評価のみの実行 | その実行IDへの要求で評価と実行全体を `interrupted` とする。元の学習実行の終了状態を保持する |

中断要求が自然な終了と行き違った場合は、実際の処理結果とプロセスの終了情報を使って判定する。すべての処理が成功して正常終了した場合は `succeeded`、失敗した処理がなく要求に応じて安全に停止した場合は `interrupted`、異常終了した場合は `failed` とする。学習の再開可否は停止結果と別に記録する。

異常終了や保存途中の失敗から再開する場合は、最後の有効な保存点を使う。再開はユーザーまたはエージェントが依頼する。[チェックポイントと学習再開](../20_basic_design/05_checkpoints_and_resume.md)

監視プロセスを失った場合、CLI の `wait` と `status` は worker の終了を確認して失敗を保存してから、確定した状態を返す。worker の異常終了では、`history --run RUN` の `diagnostics_saved` が指す `diagnostics.json` に標準出力・標準エラーの末尾（各 16 KiB まで）を保存する。Python 例外を捕捉したときはトレースバックの末尾も記録する。失敗箇所と原因は状態の `error.details.stage` と `error.message` に残る。
