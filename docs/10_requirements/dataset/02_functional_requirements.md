## 機能要件

| ID | 要件 |
|---|---|
| `DS-F-001` | DBから、指定した条件に合うデータを取得できること。生成サンプルについて、プロジェクト・タスクが検索項目に指定した条件の実際の適用値と、指定した実行での使用履歴を組み合わせて検索できること |
| `DS-F-002` | 固定データはその版を指定して同じ構成を取得できること。学習時に選択・生成するデータは、実際に決まった入力・生成条件・使用履歴から、当該実行で使ったデータを復元できること |
| `DS-F-003` | 生成データをレシピ・実体・両方の方式で登録できること。生成サンプルを学習に初めて使う前に、そのサンプルIDに使用時のレシピをDB上で対応付けること。Dataset がDBだけを参照して入力、生成手順と版、実際に適用した条件を特定できること。対応付けられない場合は学習に使用できない理由を返すこと |
| `DS-F-004` | 保存済みレシピを再生成用に取得し、プロジェクト・タスクで事前に定めた一致基準で再生成結果を照合できること |
| `DS-F-005` | 元データ、生成物、正解データ、ラベルの対応関係を辿れること。複数のDBから入力を組み合わせた場合も、返したサンプルから各入力のIDと版を特定できること |
| `DS-F-006` | データ分割間の重複検査はDatasetの個別実装に委ねる。検査の要否、判定単位、検出時の扱いは各実装が定める |
| `DS-F-007` | 呼び出し側が学習に実際に用いた時点で使用を記録し（`add`）、実行ごとの使用履歴をDBから復元できること。手法に応じて順序や反復を復元し、同じ使用記録の再送は一度と数えること。生成・ロード・先読みだけのサンプルは使用履歴に含めず、その記録の保持・削除は個別実装に委ねる |
| `DS-F-008` | データやレシピの必要情報・参照先・整合性を検証できること |
| `DS-F-009` | 登録状態を確認し、失敗した登録を再試行できること |
| `DS-F-010` | Datasetの公開インターフェースから、保存先や保存形式を指定せずに、サンプルの内容、識別子、内容の解釈に必要なメタデータを取得できること |
| `DS-F-011` | 設定で指定されたDataset実装を、共通の公開APIから利用できること。契約に適合する実装の追加時は、Datasetの共通部分の編集を要しないこと |
| `DS-F-012` | バッチの有無と範囲はTrainerなどの呼び出し側が定めること。バッチを使う場合、同じバッチの使用内容をDBから全プロセスを合わせて取得でき、プロセスを指定しても取得できること。バッチを使わない手法でも使用を記録できること |
| `DS-F-013` | 中断時も受領済みの使用記録を参照できること。分散バッチでは、呼び出し側が定めた構成に対して記録が完了したかを確認でき、未受領のプロセスの使用状況を未確認として識別できること |
| `DS-F-014` | 再開に対応する手法では、候補の保存点とそこに反映された使用履歴の範囲を対応付け（`commit`）、Experimentが再開可能な保存点として公開する前に対応付けの完了を確認できること。中断しても、最後の有効な保存点より後に受領した使用記録を元の実行から参照できること |
