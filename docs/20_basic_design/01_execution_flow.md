# 実行フロー

Experimentが実行を受け付け、個別のTrainerやEvaluatorを起動し、結果を記録する流れを定める。[Experimentの要件](../10_requirements/experiment/01_scope.md)

## 実行の準備と受付

枝の作成・実行の起動・学習の再開では、要求IDを任意で指定できる。受付済みのIDで同じ依頼が届いた場合は、新規受付に進む前に初回の結果を返す。初回の実行が既に終了していても同じ扱いとし、分岐と起動を一度に依頼した場合は元の枝IDと実行IDを返す。同じIDで操作や依頼内容を変更した場合は理由を返して拒否する。要求IDを省略した呼び出しや、新しい要求IDを指定した呼び出しには通常の受付規則を適用する。[Experimentの公開インターフェース](../30_detailed_design/01_experiment_api.md#要求の再送)

1. ユーザーやエージェントが、読み取り権限のあるDBや利用可能な実験記録から過去の結果を確認し、使う実装・設定と実行する枝を選ぶ。
2. Experimentが設定をパースし、指定された個別実装をインポートする。各実装の契約に従って設定を検証し、適用する設定と実装の版を確定する。設定やインポートに不備があれば、実行IDを発行せず、理由を呼び出し側に返す。
3. Experimentは同じ枝で一度に一つの実行を受け付ける。占有中の枝への別の起動要求には `branch_busy` と進行中の実行IDを返す。別の枝の実行は並行して進められる。
4. Experimentは受け付けた実行にIDを発行し、呼び出し側に返す。呼び出し側はそのIDで状態と結果を取得できる。受付後に起動や処理が失敗した場合は、発行済みの実行IDに理由を記録する。

学習を起動する操作は、枝が空いた時点の学習開始記録から選ぶ。学習の開始は、開始状態を保存した後、最初の学習更新に入る前に記録する。

| 枝の履歴と目的 | 次の操作 |
|---|---|
| その枝で学習が一度も始まっていないことを確認できた | 同じ枝で学習の `start` を新規に依頼できる。前の実行の終了状態と理由も履歴に残る |
| 学習を開始した実行があり、その続きを行う | 同じ枝で `resume` を依頼する。最後に学習を開始した実行と、そこから選んだ保存点を新しい実行に記録する |
| 学習開始後に最初から、または過去の地点からやり直す | 設定が同じでも新しい枝を作り、学習の `start` を依頼する |

## 学習と評価の組み立て

| 実行する処理 | 分担 |
|---|---|
| 学習 | Experimentが確定した設定でTrainerを起動する。個別のTrainerが、必要なDataset・Transform・Modelを各モジュールの公開APIから組み立てる |
| 評価のみ | Experimentが確定した設定でEvaluatorを起動する。個別のEvaluatorが必要な部品を各モジュールの公開APIから組み立てる。保存済みのモデルを使う場合はModel経由で状態をロードし、予測結果が指定されていればそのデータを使う |
| 学習中の逐次評価（標準） | Trainerがその時点のモデルと評価条件をEvaluatorに渡す。集計結果と完了状態を受け取ってから、次の更新や早期終了を判断する |
| 同じ実行での並行評価 | 個別実装は、評価開始時のモデル状態を評価終了まで固定し、Trainerの更新とEvaluatorの処理を並行して進められる |
| 学習後の評価 | タスクの実装が保存点を選んでIDを渡す。Experimentはその保存点を評価に使い、実際に評価したモデル状態を記録する |
| 後日追加する評価 | Experimentが評価だけの新しい実行IDを発行する。プロジェクト内のモデル状態や予測成果物には生成元の実行を、外部の予測ファイルには受付時に取り込んだ実体を対応付ける |

学習が成功しても評価候補が0件の場合、実行中のタスクが実験の意図に照らして見送りか失敗かを判断し、実行終了前にその扱いと理由をExperimentへ渡す。「条件を満たすモデルができたら評価する」という意図で見送った場合は評価を `skipped`、実行全体を `succeeded` とする。評価が実験の目的で実施できなかった場合は評価・実行全体を `failed` とする。どちらも学習は `succeeded` として残し、報告された理由は `status` の評価段と `history` の処理記録から確認できる。評価の必須・任意を共通configに宣言する必要はない。

学習と評価で共通する構築・ロードには各モジュールの公開APIを使う。どの部品をどの順序で使うかは、個別の学習・評価手順が決める。

全方式で、実行IDから各回の評価ID、適用条件、確定済みの対象別結果を辿れる。モデルを評価したときは、その状態を一意に特定できるようにする。評価時点の重みを後から復元できるように保持する範囲は、プロジェクト・タスクが選ぶ。[評価結果の記録](../30_detailed_design/09_evaluator.md#評価中の記録)

## 状態と記録

Experimentは実行IDごとに実行全体の状態を記録し、学習と評価それぞれの状態・結果を関連付ける。実行全体の状態は、受付済み、実行中、成功、失敗、中断を基本とする。設定された処理がすべて成功すれば全体を成功とする。学習が成功して評価が失敗した場合は、全体を失敗とし、学習の成功と成果物、評価の失敗理由を保持する。そのモデルを使って評価だけを再実行できる。

同じ実行計画で学習と評価を並行している間に一方が失敗しても、すでに進行中の他方が単独で続けられる場合は原則として続行する。評価結果が次の学習更新に必要な場合はTrainerが打ち切りを判断する。続行中は実行全体を `running` とし、他方が成功しても全体を `failed` とする。学習が先に成功した場合も、進行中の並行評価が終了してから全体の成否を確定する。

学習後に評価する逐次計画で学習が失敗した場合、Experimentは後続評価を起動せず、評価を `skipped`、理由を「前段の学習が失敗したため」と記録する。その時点で実行全体は `failed` となる。有効な保存点があれば、その保存点を指定して後日評価だけを起動できる。後日追加した評価の成否は新しい実行IDに記録する。

停止要求は実行IDを単位に扱う。Experimentは進行中の学習・評価に要求を伝え、安全に停止した処理を `interrupted` として記録する。並行する一方の失敗が確定した後で他方を停止した場合は、停止を確認した時点で実行全体を `failed` とする。逐次計画で学習を中断した場合は、実行全体も `interrupted` とし、未開始の後続評価を `skipped`、理由を「前段の学習が中断されたため」と記録する。学習成功後に評価を打ち切った場合、学習は成功のまま、評価と実行全体は中断となる。確定済みの結果・ログ・成果物は元の実行から参照できる。[実行状態と中断要求](../30_detailed_design/03_execution_state_and_processes.md#中断要求)

通信が途切れて状態を確認できない間は、最後に確認した状態と、現在は確認できないことを表示する。終了を確認できた時点で、終了状態を確定する。それまでに受け取った結果・ログ・成果物は保持し、同じ枝の次の実行は元のプロセスの終了を確認してから受け付ける。

Experimentは実行ごとに結果とログの共通の受け口を用意する。TrainerとEvaluatorは結果と、個別実装が生成したログをそこに渡す。ログの内容と粒度は個別実装が決める。学習中の評価も、どの学習実行のどの時点で行われたかを識別できるようにする。受け取った内容の記録・保管はExperimentが担う。個々の評価とAPIで報告された判断はストアのイベントに、失敗時のプロセス出力は実行の診断成果物に保存する。

## 別の作業ディレクトリへの移動

同じプロジェクトの運用先は一度に一つとする。別のクローンに運用先を移す場合は、移動元で実行を終了または中断し、履歴と状態の復元に必要な正本を移す。

移動先では、枝と実行のID・順序・分岐関係が保たれ、元の作業ディレクトリを参照せず同じDBの記録、ログ、成果物を取得できることを確認する。中断した学習は、対応するチェックポイントがあれば、移動先で同じ枝から再開できる。[実行基盤と履歴の参照](06_execution_and_replay.md)
